## Context

使用者每週在 Opus 4.8 主導的單一 session 內依序執行 `/generate-report` → `/meeting-prep` → `/sync-db` 做 SEO 盤點。本計畫盤點三個 command 檔與其驗證機制，找出可提升產出品質、可省 token、更貼合 Opus 4.8 模型特性（effort、平行工具呼叫、subagent 委派、自我驗證）的調整點，且不得回歸既有 eval 基線。

**重要修正（審查 live 查核確認）**：MEMORY.md 記錄的「`eval_meeting_prep_structure.py` 與現行報告格式漂移」待辦**已過時**——PR #51（`git show 9f0a780`，2026-07-03）已修復：`evals/eval_meeting_prep_structure.py:117-129` 的 `_EXPECTED_SECTIONS` 現為 `Section N：...` 格式，與現行報告完全對齊，並有專屬 `eval/golden_meeting_prep_structure.json`。本計畫因此可將 structure eval 一併納入自動化驗證閘門（不再只依賴 grounding eval），並在 Phase 3 修正 MEMORY.md 中的過時待辦。

**範疇聲明**：本計畫為輕量文件優化（僅調整三個 command 檔的提示內容與收尾驗證），不含未來新增例行指令或模型換代（如 Opus 5.x）的擴充規劃；若發生模型換代，僅 S1.6/S1.7/S1.8 中的 effort/subagent 建議段落需要重新審視，其餘步驟（eval 閘門、平行呼叫提示、續用邏輯）與模型版本無關。

## Architecture Notes

1. **自動化 eval 閘門取代純自我計數**：替代方案「維持純 LLM 自數」被否決——不符「驗證不自驗」，且已有零成本 rule-based script 可複用。token 影響：+1 次 Bash + ~100-300 tokens stdout，抵銷原本內部推理計數的等量消耗。不改 eval 程式碼，僅新增呼叫時機，與 pipeline 相容。
2. **顯式平行工具呼叫提示**：替代方案「依賴 Opus 4.8 原生高成功率」被否決——官方量化顯式提示可推近 100%；本工作流有 6+7-10 道獨立呼叫，效益明確，成本僅 ~40-60 字。零 eval 風險（不改蒐集內容，只改調度）。
3. **同 session 續用採軟硬雙訊號**：替代方案「一律完整重讀」保留為預設 fallback；「跨檔 hash 核對」被否決——report 與 meeting-prep 的 hash8 各自獨立雜湊，無共通值（審查第 1 輪抓出的設計錯誤）。硬訊號以 `generated_at` 為必要欄位、`snapshot_id` 選配（審查第 2 輪確認真實樣本缺此欄位）。
4. **不將 meeting-prep 靜態框架表抽成獨立參考檔**：S0-S10 每次執行都用到全部框架，抽出只是延後載入，總 token 不減反可能因往返略增，維持內嵌。
5. **不改用 API-backed 資料源**（trends / maturity-trend endpoints）：需啟動 API server + Supabase 依賴，違反「本地優先執行」偏好（`memory/feedback_local_first.md`），排除。
6. **sync-db 委派範圍收斂為唯讀**：替代方案「連非 --force upload 一併下放」被否決——upload 即是對共享資料表的寫入，下放會讓決策層級與寫入權限脫鉤（審查第 1 輪抓出）。
7. **保留硬性 checklist 措辭不精簡**：通用「精簡 prompt」建議讓位於專案實證——learned skills 記錄壓縮 Tier-1 字面標記導致 eval 分數震盪；S1.1/S1.9 的精簡刻意避開這些區塊。

## Security / Threat Model

本計畫僅修改 `.claude/commands/*.md` 三份 Markdown 文件（及可能的 `seo-qa-pipeline.md` 一行紀錄），不涉及 auth、新 endpoint、secret，不改 `api/scripts/sync-db.ts` 程式碼。**但 S1.8 的委派指引觸及「哪些操作可下放 subagent」的邊界**——非 --force 的 `make sync-db` 仍是對共享 Supabase（`SUPABASE_SERVICE_KEY`，bypass RLS）的真實寫入。已依 `repo-ownership.md` 原則收斂：僅唯讀（status/dry-run）可委派，一切寫入留主線執行或先經主線確認。除此之外無其他安全敏感面。
